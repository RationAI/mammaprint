# L2 stain and rotation implementation plan

## Experiment

Use the existing L2 cancer-mask-0.5 train and validation split and the slide-mean linear MammaPrint regressor. Keep every tile in each bag. The first training arm chooses clean or mild stain jitter independently for each training slide fetch, with probability 0.5. Validation uses the clean full bags and the original minimum-`valid/loss` checkpoint rule. Read validation MAE at that checkpoint and pair the results by seed. The archive has logged MAEs for seeds 0, 1, and 2. The checkpoint audit confirmed seed 1's saved weights. Treat the other two MAEs as historical context for this comparison until the corresponding best checkpoints are verified or clean controls are refit.

Run the rotation probe on a frozen set of validation slides spanning the index range, tile counts, and available sites or scanners. Compare each saved checkpoint's predictions on the same clean tiles at 0° and 90°. Record the paired change in predictions and MAE. Choose a practical minimum mean absolute score shift before inspecting metrics and require it to exceed clean re-embedding drift. If orientation sensitivity is material, make the rotation-only training artifact and run its own clean-plus-rotation arm. Run the combined arm only after selecting the single-transform result or explicitly deciding to test their interaction. The combined view applies both transforms to the same tile.

## Implementation

1. **Freeze the exact historical tile bags.** Build an L2-specific manifest against the pinned raw tiling and clean embedding splits on a CPU allocation. Take coordinates in clean Parquet row order. Check raw tile membership, the mapping split, and record disjointness. Require 224 × 224 square crops and unique IDs and coordinates. Exclude historical empty bags and missing labels using the linear loader's eligibility rule. Preserve the source slide path and each WSI's OpenSlide pyramid level and level-relative pixel coordinates. Write a selection digest and per-slide coordinate digests. Freeze an explicit list of eligible validation slide stems before scoring.
2. **Generate one view at a time on A40.** Reuse the embedding worker's cross-slide batches, pinned transfers and bounded asynchronous writer. Apply the view to the uint8 RGB inputs on the A40 before ImageNet normalization. Use independent hematoxylin and eosin scale factors drawn once per slide from `[0.90, 1.10]`, shared by its tiles. Retain the stain residual and near-white background. Use `90°` without interpolation for the probe and one reproducibly selected nonzero quarter-turn per training slide for full rotation. Keep physical coordinates and tile order. Bind `clean`, `stain`, `rotation`, or `stain-rotation` together with the seed, encoder revision, runtime, precision and frozen input to resumability. Use FP32.
3. **Prove the clean control.** The historical L2 config leaves the HF revision unpinned. Record the evidence used to identify it. Compare fresh and archived clean vectors and predictions on matched coordinates. Confirm crop geometry, RGB compositing and normalization. Pin parity tolerances and require each checkpoint used for prediction to match the logged minimum `valid/loss`. If the encoder or prediction-parity comparison is unresolved, generate fresh clean train and validation views and rerun the matched baselines. After selection, use a separately approved clean embedding job to make the same-encoder held-out test view before any scoring on that split.
4. **Publish matched training views.** Save per-slide Parquets with the historical coordinate keys and 2,560-dimensional FP32 embeddings. Use the existing writer and verification receipts to resume from completed slides. Generate a Hydra card only after verifying complete outputs and matching coordinates. The card keeps clean train, validation and test URIs and supplies one extra training URI. A probe bundle contains only its frozen validation subset and is kept out of training cards.
5. **Use one full training view per slide fetch.** Extend `SingleScaleDataset` to accept one explicit augmented training URI from its data card. Validate the matching slide IDs and ordered coordinates before using the view. Choose the bag from a dedicated seed stream, separate from slide shuffling and tile sampling. Save this stream with the existing Lightning data state where supported. The archived all-tile loader uses zero workers, which is the initial comparison recipe. Keep the existing linear model, optimizer and stopping policy. Save matched validation MAE, Spearman and sign-AUROC, with the held-out test reserved for a selected recipe. Rank metrics for the archived baselines can be collected by validating their saved checkpoints.

## Entry points

- `preprocessing.l2_augmentation prepare` freezes the historical tile bags. `embed` runs a bounded profile or an entire frozen selection inside one A40 allocation. `card` verifies receipts and coordinates before writing a Hydra data card. Use an immutable WSI snapshot, including companion files such as MRXS payloads. The worker checks the main file's size and modification time against the frozen manifest.
- `scripts.preprocessing.run_l2_augmentation_a40` renders an offline manifest, scopes its writable mount to the output subtree, and records host and device telemetry there. Pin the source commit, image digest and model revision for the full run.
- `scripts.preprocessing.score_l2_rotation_probe` verifies checkpoints and reports clean parity and the 90° effect on the frozen validation probe. For a fresh-control comparison, freeze the follow-up probe against the fresh validation artifact and score an audited checkpoint trained on the matched clean views.
- `ml/train.py` with `+experiment=ml/train_mil_embeddings_l2_augmentation` uses the full-bag linear preset with split checks, the view seed, validation rank metrics and validation-only fits. See the [runbook](../../../.agents/skills/l2-embedding-augmentation/SKILL.md) for arguments and examples.

## A40 sizing and checks

- Start the bounded pilot on one full A40 with 24 vCPUs, 64 GiB host RAM, 12 GiB `/dev/shm`, 32 GiB local scratch and 40 GiB pod ephemeral storage. Use the same durable shared output backend in pilot and production. If switching to direct MLflow upload, benchmark a frozen subset on that backend before extrapolating throughput. Size durable storage at 10,240 feature bytes per tile before compression, plus Parquet and receipt overhead. Fit scratch may stage the 132.25 GiB clean train and validation pair plus the augmented train artifact. Size this separately for each active fit or reuse shared read-only local data.
- Test batch and worker settings `512/8`, `1024/8`, `1024/12` and `1536/12` at prefetch 2 on identical representative slides. At the two largest profiles, the prefetched 224 × 224 uint8 RGB inputs alone use about 3.45 and 5.17 GiB respectively. The live footprint also includes worker processes, pinned transfers, the active batch, queued vectors and file cache. Use the stain view for the CPU-heaviest pilot. Repeat the best profiles in alternate order to check cache effects. For a profile that exhausts VRAM or shared memory, keep the failed measurements and test a smaller profile.
- Record committed tiles/sec, loader wait, GPU inference time, writer wait, sampled host RAM, shared memory, GPU utilization and reserved VRAM. Choose the fastest stable profile with roughly 20% headroom in measured VRAM and host memory, then retest with a smaller RAM allocation if the pilot shows equivalent throughput. Increase workers or read bandwidth when the GPU waits on the tile loader. Investigate upload bandwidth when writer wait dominates. Set the full job request and limit to the measured profile. Project full-job GPU hours from the frozen tile count and the sustained rate. Full utilization is a measured outcome on the A40.
- Verify deterministic nonidentity transforms, exact coordinate order, split isolation, resume identity, complete inventory, source and destination separation, and clean fallback. Exercise a synthetic fixture end to end and render the A40 manifest locally. Check GPU type, CPU, RAM, `/dev/shm`, scratch, and the read/write mounts in the rendered manifest.
- Obtain explicit approval after showing the exact target cluster, namespace, job, hardware profile and data scope for each cluster submission.
